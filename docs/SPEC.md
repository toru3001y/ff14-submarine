## 1. 概要

FF14（Final Fantasy XIV）の潜水艦システムにおいて、パーツ（艦体・艦尾・艦首・艦橋）と
潜水艦ランクの組み合わせから、最終的なステータス値（探査・収集・巡航・航続・運）および
コスト・キャパシティを計算するツール。

| 項目 | 内容 |
|---|---|
| 形式 | Vite + React + TypeScript のSPA（ビルドあり） |
| 配信 | Cloudflare Workers Static Assets（純静的・Workerスクリプトなし） |
| 実行時の外部依存 | **なし**（外部CDN・外部フォントサービスを使用しない） |
| サーバーサイド処理 | なし。計算は全てクライアントで完結 |
| 永続化 | なし（localStorage・Cookie等を使用しない） |
| 想定利用者 | FF14プレイヤー |
| 対応環境 | **PC のみ（ビューポート幅 960px 以上）**。960px 未満は対応対象外とする |

### 1.1 前提

`old/` に旧アプリの実行可能なHTML本体は存在しない。残っているのはデータ2本
（`parts-data.js` 40件、`rank-bonus-data.js` 135件）、仕様書、旧UIスクリーンショット、
UIモックアップのみである。したがって本プロジェクトは既存コードの移植ではなく、
**仕様書とデータからの再実装**である。引き継ぐ制約はデータの値と計算式のみ。

`old/` 配下は変更しない。データ整合性テストのフィクスチャとして参照する（§8.2）。

### 2.1 v1.0 の欠陥（修正対象）

v1.0 仕様の 2.1 と 2.4 は、単独では妥当だが組み合わせると破綻する。

- 2.1: ランク未入力時の表示は「キャパシティ**0**」
- 2.4: チェック条件は「コスト合計 > キャパシティ」

この2つを素直に実装すると、**ランク未入力の状態でパーツを1つ選んだ瞬間に
コスト5 > キャパシティ0 が成立し、超過エラーが表示される**。ユーザーは何も
誤っていないのに警告が出る。原因は「未入力」と「ランク1」を区別していないこと。

v2.x ではランクを3状態の判別可能な型として表現し、有効なときだけ判定する（§3.1、§3.4）。

## 3. 機能要件

機能は5つ。v1.0 の6機能から Excelエクスポートを除いたもの。

### 3.1 潜水艦ランク入力

#### 3.1.1 入力欄の仕様

| 項目 | 内容 |
|---|---|
| 要素 | `<input type="text">` |
| 範囲 | 1 〜 `MAX_RANK`（現在135） |
| `maxlength` | **設定しない**（理由は §3.1.2 の注記） |
| プレースホルダ | `1-{MAX_RANK}` |
| 状態 | `empty` / `invalid` / `valid` の3状態（§3.1.4） |
| 値の書き換え | 入力中は書き換えず、`blur` 時に `valid` なら正準表現へ整形する（§3.1.3） |

`MAX_RANK` はハードコードせず**ランクボーナステーブルから導出する**。
プレースホルダ、エラーメッセージ、↑↓キーの上限も全てこの導出値を参照する。
これにより上限が拡張されたとき、変更箇所はデータファイル1つだけになる。

> **`type="text"` は入力値を数字に制限しない。**
> キーボード・ペースト・IME からは任意の文字列が入る。したがって §3.1.2 の
> 解釈規則が唯一の防壁である。

#### 3.1.2 入力値の解釈規則

以下の手順で正規化・判定する。

1. 前後の空白を除去する（半角スペース `U+0020`、全角スペース `U+3000`、タブ `U+0009`）
2. 全角数字（`U+FF10`〜`U+FF19`）を半角数字に変換する
3. 結果が空文字なら `empty`
4. `/^[0-9]+$/` にマッチしなければ `invalid { reason: 'notInteger' }`
5. 10進整数として解釈し、`1 <= n <= MAX_RANK` でなければ `invalid { reason: 'outOfRange' }`
6. それ以外は `valid { rank: n }`

| 入力 | 正規化後 | 判定 | 備考 |
|---|---|---|---|
| `""` | `""` | `empty` | 初期状態 |
| `"   "`（空白のみ） | `""` | `empty` | 全角スペースを含む |
| `" 80 "` | `"80"` | `valid(80)` | 前後の空白は除去する |
| `"01"` | `"01"` | `valid(1)` | 先頭ゼロを許容する |
| `"１３５"`（全角） | `"135"` | `valid(135)` | 全角数字を正規化する |
| `"+1"` | `"+1"` | `invalid(notInteger)` | 符号は受理しない |
| `"-1"` | `"-1"` | `invalid(notInteger)` | 符号は受理しない |
| `"1.5"` | `"1.5"` | `invalid(notInteger)` | 小数は受理しない |
| `"1e2"` | `"1e2"` | `invalid(notInteger)` | 指数表記は受理しない |
| `"12a"` | `"12a"` | `invalid(notInteger)` | 数字と文字の混在 |
| `"0"` | `"0"` | `invalid(outOfRange)` | 下限未満 |
| `"136"` | `"136"` | `invalid(outOfRange)` | 上限超過 |
| `"99999999999"` | 同左 | `invalid(outOfRange)` | 桁数制限は設けない |

**判断とその理由**

- **符号（`+` / `-`）を受理しない**: ランクは常に正の整数であり、符号を許すと `"+1"` と `"1"` という2通りの表現が生まれる。表現を一意に保つため
- **先頭ゼロを許容する**: `"01"` は十進表記として自然で、意図が一意に定まるため
- **全角数字を正規化する**: 日本語IMEでの入力で頻出し、拒否するのは利用者にとって理不尽であるため
- **小数・指数表記を受理しない**: ランクは整数であり、`1.5` や `1e2` を解釈すると「入力した文字列」と「解釈された値」が乖離して混乱を招くため
- **`maxlength` を設定しない**: 編集途中（全選択して打ち直す等）にキーストロークが黙って落ちるほうが、明示的なエラー表示より原因が分かりにくいため。桁数の妥当性は `outOfRange` として明示的に伝える

**エラーメッセージ**

| 理由 | 文言 |
|---|---|
| `notInteger` | `ランクは数字のみで入力してください` |
| `outOfRange` | `ランクは1〜{MAX_RANK}の範囲で入力してください` |

`notInteger` の文言に「半角」と書かない。全角数字は §3.1.2 の手順2で受理するため、
「半角数字で入力してください」は仕様と矛盾する。拒否しているのは符号・小数点・
指数表記・数字以外の文字であり、「数字のみ」がその実態を正しく表す。

#### 3.1.3 入力欄の値の書き換えタイミング

§3.1.2 は入力文字列をどう**解釈**するかを定めるものであり、DOM 上の入力値を
書き換えるかどうかは別問題である。書き換えの契機を以下に確定する。

| 契機 | 入力欄の値 | 判定・表示 |
|---|---|---|
| 入力中（`input` / `change`） | **書き換えない。** 利用者が打った文字列をそのまま保持する | リアルタイムに再判定し、エラー・ボーナス・総合値を更新する |
| IME変換中（`compositionstart` 〜 `compositionend`） | 書き換えない | **判定を保留し、直前の判定結果を維持する**。`compositionend` 後に再判定する |
| フォーカスを失ったとき（`blur`） | 判定が `valid` のときのみ、正準表現（半角・先頭ゼロなし・前後空白なし）に書き換える。`empty` / `invalid` のときは**書き換えない** | 変化なし |
| ↑↓キー操作時 | 算出された整数を正準表現で書き込む | 再判定する |
| リセット時 | 空文字にする | `empty` になる |

正準表現への書き換え例（`blur` 時）:

| blur 前の入力欄 | 判定 | blur 後の入力欄 |
|---|---|---|
| `" 80 "` | `valid(80)` | `80` |
| `"１３５"` | `valid(135)` | `135` |
| `"01"` | `valid(1)` | `1` |
| `"12a"` | `invalid(notInteger)` | `12a`（そのまま） |
| `"136"` | `invalid(outOfRange)` | `136`（そのまま） |
| `"   "` | `empty` | `   `（そのまま。表示は空白のみで実害がないため触らない） |

**判断とその理由**

- **入力中に書き換えない**: 入力途中で値を差し替えるとキャレット位置が末尾へ飛び、
  文字列の途中を編集できなくなる。`"135"` の先頭に `2` を挿して `"2135"` にしようとした
  瞬間に `outOfRange` としてクランプされるような挙動も避ける
- **IME変換中は判定を保留する**: `"１３５"` を IME で入力する間、未確定文字列に対して
  `onChange` が発火する。都度判定するとエラーメッセージが点滅し、`aria-live` が
  未確定文字列を読み上げてしまう
- **`blur` で `valid` のときだけ正準化する**: 確定した値のみを一意な表現に揃える。
  不正値を勝手に整形・消去すると、利用者が何を打ったのか分からなくなり修正できない
- **`"01"` を `"1"` にする**: 解釈結果と表示を一致させるため。解釈上 `01` と `1` は
  同一であり、確定後に2通りの表示が残る理由がない
- **↑↓は常に正準表現を書き込む**: 算出結果は整数値そのものであり、元の表記を
  保持する意味がない

#### 3.1.4 状態ごとの表示

| 状態 | 入力欄の下線 | エラーメッセージ | ランクボーナス表示 | 超過判定 |
|---|---|---|---|---|
| `empty` | `--ink` | なし | 全項目 `—` | **行わない** |
| `invalid` | `--danger` | 表示する | 全項目 `—` | **行わない** |
| `valid` | `--ink`（focus時 `--accent`） | なし | 当該ランクの値 | 行う |

#### 3.1.5 ↑↓キーによる増減

入力欄にフォーカスがあるときのみ動作する。キー押下時は `preventDefault()` を呼び、
ページスクロールを抑止する。

| 現在の状態 | ↑ の結果 | ↓ の結果 |
|---|---|---|
| `empty` | `1` | `MAX_RANK` |
| `valid(v)`（`1 < v < MAX_RANK`） | `v + 1` | `v - 1` |
| `valid(1)` | `2` | `1`（変化なし） |
| `valid(MAX_RANK)` | `MAX_RANK`（変化なし） | `MAX_RANK - 1` |
| `invalid(outOfRange)` かつ `n > MAX_RANK` | `MAX_RANK` | `MAX_RANK` |
| `invalid(outOfRange)` かつ `n < 1`（`"0"` 等） | `1` | `1` |
| `invalid(notInteger)` | 変化なし | 変化なし |

**判断とその理由**

- **ラップアラウンドしない**（135で↑を押しても1に戻らない）: 誤操作で意図しない大ジャンプが起きるため
- **`empty` で ↑ が `1`、↓ が `MAX_RANK`**: 「何もない状態から上へ」は下端から、「下へ」は上端から入る、という対称的な解釈。両端に1打鍵で到達できる利点もある
- **`invalid(outOfRange)` はクランプする**: 整数として解釈できている以上、最も近い有効値へ寄せるのが利用者の意図に近いため。押されたキーの向きに関わらず有効域へ入れる
- **`invalid(notInteger)` は何もしない**: 入力途中の文字列を勝手に置換すると、利用者が打った内容が失われるため
- **キーリピート（押しっぱなし）を抑制しない**: 連続増減は有用であり、範囲は上下限でクランプされるため暴走しない

### 3.3 総合ステータス

#### 3.3.1 計算

| 項目 | 内容 |
|---|---|
| 計算式 | 総合値 = Σ(選択中4部位のパーツ性能値) + ランクボーナス値 |
| コストの扱い | コストのみランクボーナス対象外。総コスト = Σ(選択中パーツのコスト) |
| 未選択部位 | **0として扱う**（部分的な選択でも合計を表示する） |
| 表示項目 | コスト・探査・収集・巡航・航続・運 の6項目 |

#### 3.3.2 ランクが `empty` / `invalid` のときの扱い

**v1.0 の挙動を継承し、ランクボーナスを 0 として、選択済みパーツの合計を表示する。**

| 項目 | 表示 |
|---|---|
| 5ステータスの総合値 | ランクボーナスを0とした、選択済みパーツの合計値（数値） |
| コスト（分子） | 選択済みパーツのコスト合計（数値） |
| キャパシティ（分母） | `—` |
| キャパシティ超過判定 | **行わない**（§3.4） |
| セクション01 のランクボーナス ミニグリッド | 全項目 `—` |

総合値を `—` にしない理由: 「未選択部位を0として扱う」規則を一貫させると全未選択時の合計は0になる。
また総合値を `—` にすると、部分選択時に「一部が数値・一部が `—`」という不整合が生じる。
ランクボーナスが不明であることは**キャパシティの `—` とランクボーナス行の `—` で示す**。

#### 3.3.3 ゼロと符号の表示規則

| 箇所 | 正の値 | 0 | 負の値 |
|---|---|---|---|
| セクション03 総合ステータス（44px） | `210`（符号なし） | `0` | `-20` |
| ミニグリッド（選択済みパーツ・ランクボーナス） | `+30`（符号あり） | `0` | `-10` |
| コスト | `58` | `0` | （負にならない） |
| 未選択・ランク未確定 | — | — | `—` を表示 |

- **`+0` は使わない。** 0 に符号を付けても意味を持たない。ミニグリッドの値は mono（数字が等幅）で
  表示する
- **ミニグリッドのみ `+` を付ける理由**: ミニグリッドは「加算される差分」であり符号が意味を持つ。総合ステータスは「結果の値」であり、負のときのみ `-` が付く

#### 3.3.4 初期状態

ランク未入力・4部位すべて未選択のとき。

| 項目 | 表示 | 色 |
|---|---|---|
| コスト | `0 / —` | 分子 `--ink`、分母 `--text-muted` |
| 探査・収集・巡航・航続・運 | すべて `0` | `--ink` |
| セクション01・02 のミニグリッド | すべて `—` | `--text-muted` |

### 3.4 キャパシティ超過判定

| 項目 | 内容 |
|---|---|
| 判定条件 | ランクが `valid` **かつ** コスト合計 > 当該ランクのキャパシティ |
| 警告表示 | 「03 総合ステータス」見出し行の右端に `--danger` で1行。超過量を含める（例: `⚠ キャパシティを 5 超過`） |
| 数値の変化 | コスト数値を `--danger` にする。アニメーションは行わない |
| レイアウト | 警告の有無で高さが変わらないこと（見出し行の既存の空白を使う） |
| 判定タイミング | パーツ選択変更時・ランク変更時にリアルタイム再計算 |

**補足（実装上の性質）**: パーツコスト合計の最大は 80（全部位を改級にした場合）、
ランク50以降のキャパシティは 80 で固定である。`80 > 80` は偽であるため、
**キャパシティ超過はランク1〜49でのみ発生し得る**。テストケース設計時にこれを踏まえること。

### 3.5 リセット

| 項目 | 内容 |
|---|---|
| トリガー | 「選択をリセット」ボタン |
| 動作 | ランク入力・4部位の選択・全表示・エラー状態を初期状態に戻す |
| 初期状態 | ランクは `empty`、4部位とも未選択（§3.3.4 の表示になる） |
| フォーカス | リセット後もボタンにフォーカスを残す（フォーカスを失わせない） |

## 4. データ仕様

### 4.1 パーツデータ（40件・追加予定なし）

各パーツは以下から構成される。

| フィールド | 型 | 意味 |
|---|---|---|
| `slot` | `Slot` | 部位。`hull` / `stern` / `bow` / `bridge` |
| `series` | `Series` | 系統。`shark` / `unkiu` / `whale` / `coelacanth` / `syldra` |
| `improved` | `boolean` | 改級かどうか |
| `cost` | `number` | パーツコスト |
| `stats` | `Stats` | 探査・収集・巡航・航続・運（負値あり） |

**パーツ名は保持せず導出する。** 40件すべてが次の規則に従う。

```
name = {系統ラベル} + (improved ? "改級" : "級") + {部位ラベル}

例: シャーク + 級   + 艦体 = "シャーク級艦体"
    シャーク + 改級 + 艦体 = "シャーク改級艦体"
```

導出結果が旧データの40件と完全一致することはテストで保証する（§8.2）。
これにより、系統・改級が名前文字列にしか存在しないという v1.0 の構造的問題が解消し、
`<optgroup>` の構築に文字列パースが不要になる。

コスト（実データより確認済み）:

| 系統 | 通常級 | 改級 |
|---|---|---|
| シャーク級 | 5 | 20 |
| ウンキウ級 | 9 | 20 |
| ホエール級 | 12 | 20 |
| シーラカンス級 | 14 | 20 |
| シルドラ級 | 17 | 20 |

### 4.2 ランクボーナスデータ（現在135件・上限拡張あり）

ランクごとに `rank` / `capacity` / 5ステータスを持つ。

実測した性質（ランク1〜135）:

| ランク帯 | キャパシティ | ステータスボーナス |
|---|---|---|
| 1 〜 49 | 20 から1ずつ増加（r1=20、r48=67、r49=68） | 全て0 |
| 50 | **80**（r49の68から跳ね上がる） | 全て0 |
| 51 〜 135 | 80で固定 | 段階的に増加 |
| 135 | 80 | 探査100 / 収集130 / 巡航90 / 航続120 / 運95 |

#### 4.2.1 拡張の扱い

将来の拡張は**上限の追加のみ**であり、既存ランク1〜135の値は変更されない。
この前提のもとで、検証を次のように分離する（§8.2 に対応）。

| 対象 | 検証内容 |
|---|---|
| ランク 1 〜 135 | 旧データ `old/rank-bonus-data.js` の該当行と各フィールドが完全一致すること |
| ランク 136 以降 | **旧データとの比較対象外**。不変条件のみ検証する |
| 全ランク共通 | 不変条件（§8.2.2）を満たすこと |

**配列全体の件数一致は検証しない。** 旧データの各ランクに対応する行が新データに存在し
値が一致すること、という方向でのみ照合する。これにより行を追加してもテストは壊れない。

#### 4.2.2 データの保持形態

| 層 | 形 | 目的 |
|---|---|---|
| `src/data/rank-bonus.ts` | フラットな1行1レコード配列 | 人間が追記・編集する |
| `src/domain/ranks.ts` | `{rank, capacity, stats}` に正規化 | コードから使う |

### 4.3 値域

未選択部位を0として扱うため、**画面に表示され得る値域は「4部位すべて選択済み」の場合より広い**。
表示幅の設計は右端の列（画面表示の値域）を根拠とする。

| 項目 | 4部位選択済み | 未選択を含む途中状態 | ランクボーナス最大 | **画面表示の値域** |
|---|---|---|---|---|
| コスト | 20 〜 80 | 0 〜 80 | 対象外 | **0 〜 80** |
| 探査 | -20 〜 190 | -45 〜 190 | +100 | **-45 〜 290** |
| 収集 | 5 〜 235 | -10 〜 235 | +130 | **-10 〜 365** |
| 巡航 | -20 〜 170 | -20 〜 170 | +90 | **-20 〜 260** |
| 航続 | -65 〜 215 | -65 〜 215 | +120 | **-65 〜 335** |
| 運 | 30 〜 170 | 0 〜 170 | +95 | **0 〜 265** |

- 「途中状態」は各部位について「最も低い値のパーツを選ぶ」と「選ばない（＝0）」のうち小さいほうを取った理論下限
- ランクボーナスは常に0以上であるため、下限はボーナス0のランク（1〜50）で発生する
- **表示され得る最大の文字数は3文字**（`365` / `-65` / `-45` など）
- **受け入れ条件**: 想定される最大値と最小値が、PCレイアウトの表示領域から
  はみ出さず判読できること。文字幅・桁位置の厳密な一致は要求しない（§5.5.2）

## 5. UI仕様

ベースは Claude Design の「Submarine Tool Final (2c 松葉)」。
1a（スイス・エディトリアル）の構造を松葉色に配色し直した版である。
原本は `old/ui-design/Submarine Tool Final (2c 松葉).dc.html`。

### 5.1 デザイントークン

背景 `#f7f6f0` に対するコントラスト比を実測して決定した。
**小さい文字に用いる色はすべて WCAG 2.2 AA（4.5:1）以上**とする。

| トークン | 値 | 対 `--bg` | 判定 | 用途 |
|---|---|---|---|---|
| `--bg` | `#f7f6f0` | — | — | 紙の下地 |
| `--ink` | `#17201a` | 15.42:1 | AA | 主テキスト、2pxの見出し罫、セクション境界線、**コスト数値**、**0の数値** |
| `--accent` | `#2f6b4f` | 5.81:1 | AA | 松葉色。eyebrow、セクション番号、**正の値**、主ボタン、フォーカスリング |
| `--accent-strong` | `#255741` | 7.70:1 | AA | ボタンの hover |
| `--danger` | `#bd4034` | 4.91:1 | AA | **負の値、キャパシティ超過、入力エラー** |
| `--text-2` | `#525a53` | 6.58:1 | AA | ラベル、セレクト内文字（プレースホルダ含む） |
| `--text-muted` | `#6b706a` | 4.67:1 | AA | 補助テキスト、行番号、単位、`(1-135)`、ミニグリッドの項目名、**未確定 `—`** |
| `--rule` | `#dcded4` | 1.26:1 | 装飾のみ | 1pxの罫線（行区切り・列区切り） |
| `--on-accent` | `#f7f6f0` | 5.81:1（対 `--accent`） | AA | 緑ボタン上の文字 |
| `--overlay-ink` | `rgba(23,32,26,0.0625)` | — | — | セカンダリボタンの hover 背景 |

モックアップの `#e2554d`（danger）・`#8b9089`・`#aeb2a9` は紙色に対して
3.44:1 / 3.01:1 / 1.99:1 しかなく AA を満たさないため、上表の値に差し替えている。

`--rule` は装飾用の罫線であり、AA の対象としない。
**操作要素の境界を示す線には `--rule` を使わない**（ランク入力欄とセレクトの下線は `--ink`）。

#### 5.1.1 色覚に関する制約（重要）

`--accent`（緑）と `--danger`（赤）は**輝度がほぼ同一**であり、
**赤緑色覚異常では正の値と負の値を色だけで区別できない。**

このため §5.3 のとおり、**負の値には必ず `-` 符号を伴わせる**。色は補助的な手がかりに留め、
判別可能性は符号が担保する（WCAG 1.4.1 適合）。同様に、キャパシティ超過は色に加えて
必ずテキスト警告を伴わせる。

### 5.2 タイポグラフィ

**OS標準フォントを使用する。** フォントファイルをアプリから配信せず、
外部フォントサービスへの通信も行わない。

```css
:root {
  --font-sans:  system-ui, sans-serif;
  --font-serif: ui-serif, serif;
  --font-mono:  ui-monospace, monospace;
}
```

| トークン | 用途 |
|---|---|
| `--font-sans` | 本文・操作要素（セレクト、ボタン、ラベル、メッセージ） |
| `--font-serif` | 見出し・部位名・ランク入力値・総合ステータスの数値 |
| `--font-mono` | eyebrow・セクション番号・行番号・単位・ミニグリッドの値 |

要件は以下に限定する。

- 本文・操作要素には OS 標準の UI 向けフォントを使う
- 見出しには OS 標準の serif 系フォントを使ってよい
- 数字・補助表示には OS 標準の monospace 系フォントを使ってよい
- **OS・ブラウザによる書体差を許容する**
- **厳密な書体・ウェイト・文字幅・桁揃えは保証しない**
- 日本語・数字・記号が判読できればよい
- フォントファイルをアプリから配信しない
- 外部フォントサービスへ通信しない

CSS の書き方は通常のプロジェクトルールに従う。
**フォント検証のためだけの記述制約（`font` ショートハンド禁止、ウェイトの数値限定、
インライン style 禁止など）は設けない。**


### 5.3 色と記号の意味づけ

| 意味 | 色 | 併用する記号 | 対象 |
|---|---|---|---|
| 正の値（高いほど良い） | `--accent` | ミニグリッドでは `+` | 5ステータスが 0 より大きいとき |
| ゼロ（中立） | `--ink` | なし | 5ステータスが 0 のとき |
| 負の値 | `--danger` | **必ず `-`** | 5ステータスが 0 未満のとき |
| 予算（良し悪しではない） | `--ink` | なし | コスト数値（通常時） |
| 問題 | `--danger` | **必ずテキスト警告を併記** | コスト数値（超過時）、超過警告、ランク入力エラー |
| 未確定 | `--text-muted` | `—` | 未選択のパーツ性能、ランク未確定時のキャパシティとボーナス |

ゼロを `--accent`（正扱い）にしない理由: 緑は「加点」を意味するため、加点0を緑にすると誤誘導になる。

### 5.4 6列ミニグリッド

セクション03（総合ステータス）が持つ「6列グリッド ＋ 左罫線」というモチーフを、
小さいスケールでセクション01・02にも反復させる。新しい視覚語彙を追加せずに、
v1.0 の課題②（一行文字列の視認性）と課題④（項目間の関連性の欠如）を解決する。

```
【セクション02 パーツ選択（PC）】
                                コスト  探査  収集  巡航  航続    運
──────────────────────────────────────────────────────────────
01  艦体   [シャーク級艦体      ▾]     5   -10   +30   +20   +40   +20
──────────────────────────────────────────────────────────────
02  艦尾   [シャーク級艦尾      ▾]     5   -30   +20   +60   +30   +15
──────────────────────────────────────────────────────────────
03  艦首   [ウンキウ級艦首      ▾]     9   +60   +20   +20   -15   +10
──────────────────────────────────────────────────────────────
04  艦橋   [艦橋を選択してください ▾]     —     —     —     —     —     —
```

※ 上図の `▾` はセレクトであることを示す説明用の記号であり、実装ではブラウザ標準のセレクト表示を用いる（§5.5）。

- 見出し行は1回だけ置く。4部位の同一項目が縦に揃うため、部位間の比較ができる
- コスト以外は符号付きで表示する（§3.3.3）
- 未選択・未確定は `—`（U+2014、`--text-muted`）
- セクション01のランクボーナスにも同じ形式を用いる（1列目はキャパシティ）
- **項目名**（`コスト` `探査` …）: `--font-sans`、色 `--text-muted`。日本語を含むため sans を用いる
- **値**（数字・符号・`—`）: `--font-mono`、色は §5.3 の規則に従う。日本語を含まない

項目名と値で書体トークンが異なる（§5.2）。

### 5.5 PC レイアウト（幅960px以上）

モックアップ「2c 松葉」は**全体デザインの参考**であり、厳密な再現対象ではない。
余白・文字サイズ・線の太さ・細かな位置は、実装時に自然に見える範囲で調整してよい。

#### 5.5.1 構成

| 項目 | 要件 |
|---|---|
| セクション構成 | **01 潜水艦ランク ／ 02 パーツ選択 ／ 03 総合ステータス** の3セクション（v1.0 の 04「選択中のパーツ構成」は削除） |
| コンテナ | 中央寄せ。基準幅は 1040px 程度とし、それ未満では幅に追従させる |
| 01 ランク | ランク入力欄と、ランクボーナスの6列ミニグリッド（§5.4） |
| 02 パーツ選択 | 4部位を縦に並べる。各行で**部位名・セレクト・性能値の6列ミニグリッドが判別できる**配置にする |
| 03 総合ステータス | **6項目を一覧できる**配置。見出し行に超過警告の居場所を確保する |
| ボタン行 | リセットボタン単独。破壊的操作のため主ボタン（緑）にはせず、枠線スタイルとする |
| セレクト | ネイティブの `<select>` を用い、**ブラウザ標準の表示のまま**とする（`appearance:none` を使わない）。選択可能であることが分かれば足りる |
| 書体の割り当て | §5.2 のトークンに従う。見出し・部位名・ランク入力値・総合ステータスの数値は serif、本文とセレクトは sans、eyebrow・番号・単位・ミニグリッドの値は mono |

#### 5.5.2 受け入れ条件

- 幅 960px 以上で、**要素の重なり・文字切れ・操作不能・意図しない横スクロールが無い**
- ランク入力欄・4つのセレクト・リセットボタンが操作できる
- 総合ステータスと超過警告が判読でき、他の操作要素に重ならない
- 想定される最大値・最小値（§4.3）が表示領域からはみ出さず判読できる
- モックアップと全体的な雰囲気が大きく異ならない
- **数px単位の位置・余白・文字幅・桁位置の一致は要求しない**

#### 5.5.3 ボックスモデル

```css
*, *::before, *::after { box-sizing: border-box; }
```

レイアウト破綻を防ぐ基本実装として全要素に適用する。
`content-box` のままだと `width:100%` に `padding` を足した要素が親からはみ出す。


## 6. アクセシビリティ要件

**WCAG 2.2 レベル AA のうち、下表 A1〜A10 の範囲を満たすことを目標とする。**
全面適合は目標としない。対象外とする達成基準を下記に明記する。

### 6.1 対象外とする達成基準

| 達成基準 | 扱い | 理由 |
|---|---|---|
| **1.4.10 リフロー**（AA） | **対象外** | 本アプリは PC・ビューポート幅 960px 以上のみを対象とし（§1）、狭いビューポート向けのリフローレイアウトを実装しない。400%拡大時に横スクロールが発生することを許容する |

> **この判断はアクセシビリティ上の後退である。** 1.4.10 は拡大表示を必要とする
> ロービジョン利用者のための基準であり、PC利用者にも該当する。
> 「PCのみ・960px未満は対応外」という方針を優先した結果として対象外にしている。
> 方針を見直す場合は、狭いビューポート向けのレイアウトを §5.5 に追加したうえで
> 本節を削除すること。

### 6.2 満たす要件

| # | 要件 | 実装方針 |
|---|---|---|
| A1 | すべての入力欄・セレクトにプログラム上のラベルを付ける | 視覚上のラベル（「ランク:」「艦体」等）をそのまま `<label for>` にする。視覚ラベルを持たないコントロールを作らない |
| A2 | 不正なランク入力に `aria-invalid` を設定する | `invalid` のとき `aria-invalid="true"`、`empty` / `valid` のとき `aria-invalid="false"` |
| A3 | エラーメッセージを入力欄に関連付ける | メッセージ要素に `id` を付け、入力欄の `aria-describedby` で参照する。メッセージ非表示時も要素は残し、内容を空にする（参照切れを防ぐ） |
| A4 | 動的なエラー・警告を支援技術へ通知する | ランクエラー領域と超過警告領域に `aria-live="polite"` を付ける。**`role="alert"`（assertive）は使わない** — 入力の1打鍵ごとに割り込み読み上げが発生し操作を阻害するため |
| A5 | キーボードフォーカスを色だけに依存せず視認可能にする | `:focus-visible` に outline を指定し、**フォーカス位置が明確に視認できる**ようにする。下線色の変化のみに依存させない（形状の変化を伴わせる）。`outline: none` を単独で使わない。太さ・オフセットの具体値は実装時に自然に見える範囲で調整してよい |
| A6 | キーボードだけで全操作を完了できる | ランク入力（文字入力・↑↓）、4つのセレクト、リセットボタンが Tab 順で到達可能。`tabindex` に正の値を使わない。フォーカストラップを作らない。DOM順と視覚順を一致させる |
| A7 | 色のみに情報を依存させない | 負の値には必ず `-` 符号を伴わせる。キャパシティ超過は色に加えてテキスト警告を伴わせる（§5.1.1 の色覚制約への対応） |
| A8 | 見出し構造を正しく組む | `h1`（ツール名）→ `h2`（各セクション見出し）。セクション番号「01」等は装飾のため `aria-hidden="true"` |
| A9 | 言語を明示する | `<html lang="ja">` |
| A10 | 動きへの配慮 | アニメーションを持たない（§2 #6）。`prefers-reduced-motion` に反応すべき要素が存在しない |

## 7. アーキテクチャ

### 7.1 レイヤ

```
 src/data/     生データ。人間が編集する層。ランク拡張時はここに行を追加する
      │ 変換 ＋ 不変条件テスト
      ▼
 src/domain/   純TypeScript。Reactに一切依存しない
      │ deriveViewModel(rankInput, selections) → ViewModel
      ▼
 src/ui/       React。ViewModel を描画し、DOM/ブラウザAPI固有の関心を担う
```

**計算・状態判定・表示値の決定は `deriveViewModel()` という1本の純関数の中で終わる。**
「ランクが未入力なら警告を出さない」「値が負なら danger 色」「コストの分母を `—` にする」
といった判断をJSXの条件分岐に埋め込まない。JavaのPresenter / ViewModelパターンに相当する。

ただし以下は純関数では表現できず、UI層の責務として残る。これらは §8.3 / §8.4 で検証する。

- キーイベント処理（↑↓）とフォーカス管理
- `<optgroup>` を含むDOM構造の生成
- レイアウトとフォーカスリングの描画

### 7.3 主要な型（骨子）

```ts
export const STAT_KEYS = ['exploration', 'harvest', 'surveillance', 'range', 'favor'] as const;
export type StatKey = typeof STAT_KEYS[number];
export type Stats   = Readonly<Record<StatKey, number>>;

export const SLOTS  = ['hull', 'stern', 'bow', 'bridge'] as const;                  // 艦体/艦尾/艦首/艦橋
export const SERIES = ['shark', 'unkiu', 'whale', 'coelacanth', 'syldra'] as const; // 表示順もこの定義順
export type Slot   = typeof SLOTS[number];
export type Series = typeof SERIES[number];

export type Part = {
  readonly id: string;        // `${series}-${improved ? 'kai' : 'std'}-${slot}`
  readonly slot: Slot;
  readonly series: Series;
  readonly improved: boolean;
  readonly name: string;      // 導出値（§4.1）
  readonly cost: number;
  readonly stats: Stats;
};

export type RankBonus = {
  readonly rank: number;
  readonly capacity: number;
  readonly stats: Stats;
};

export type RankState =
  | { readonly kind: 'empty' }
  | { readonly kind: 'invalid'; readonly reason: 'outOfRange' | 'notInteger' }
  | { readonly kind: 'valid';   readonly rank: number; readonly bonus: RankBonus };

export type Selections = Readonly<Record<Slot, Part | null>>;
```

`STAT_KEYS` を配列として定義することで、合計計算・6列グリッドの描画・性能表示が
すべてループ1本になり、項目が増えたときの変更点が1箇所に閉じる。

### 7.4 命名についての注記

`surveillance`（＝監視／偵察）が日本語の「巡航」に対応している点は語感として不自然だが、
FF14公式の英語ステータス名を一次情報で確認していないため**【未確認】**である。

v2.x では**旧フィールド名をそのまま踏襲する**。理由は、一次情報を取らずに改名すると
旧データとの完全一致テストの根拠が崩れるため。日本語表記は `labels.ts` に分離するので、
後日確認できた時点で改名しても影響範囲は閉じる。

## 8. 検証

検証を4層に分ける。**ドメインテストだけで仕様全体を検証できるわけではない。**
入力操作・DOM構造・警告表示はドメイン層に現れないため、
コンポーネントテストで担保する。レイアウトと視覚は手動確認項目で担保する。

| 層 | 対象 | 手段 |
|---|---|---|
| §8.1 ドメインテスト | 計算、ランク状態の解釈、ViewModel の生成 | Vitest（jsdom不要） |
| §8.2 データ整合性テスト | 旧データとの照合、不変条件 | Vitest（jsdom不要） |
| §8.3 コンポーネントテスト | 入力、選択、警告、リセット、ARIA属性 | Vitest + jsdom + React Testing Library |
| §8.4 手動確認 | レイアウト、フォーカス表示、フォントの描画 | チェックリスト（`tests/manual-checklist.md`） |

### 8.1 ドメインテスト

| 検証項目 | 内容 |
|---|---|
| ランク入力の解釈 | §3.1.2 の表の全行（空白、`01`、`+1`、全角、小数、指数、混在、`0`、`136`、巨大値） |
| ↑↓の値決定ロジック | §3.1.5 の遷移表の全行（キーイベント処理そのものは §8.3） |
| 正準表現への整形 | §3.1.3 の `blur` 時変換表（`" 80 "`→`80`、`"１３５"`→`135`、`"01"`→`1`、不正値は無変換） |
| `MAX_RANK` の導出 | テーブル末尾の `rank` と一致する |
| 合計計算 | 未選択部位を0として扱う。コストにランクボーナスを加算しない |
| ランク未確定時の総合値 | ランクボーナスを0として合計を返す（§3.3.2） |
| キャパシティの未確定 | ランクが `valid` でないとき分母が `—` になる |
| 偽警告の不在 | ランク未入力＋パーツ選択済みで超過フラグが立たない（§2.1 の回帰防止） |
| 超過判定 | ランク `valid` かつ コスト > キャパシティ のときのみ真。超過量が正しい |
| ゼロと符号 | §3.3.3 の表（`+0` を生成しない、負値に必ず `-` が付く） |
| 色種別の決定 | 正 → accent、0 → ink、負 → danger、コスト通常時 → ink、超過時 → danger |
| パーツ名の導出 | `series` × `improved` × `slot` から正しい名前を生成する |
| 系統グループの順序 | `SERIES` 定義順、各系統内が 通常級 → 改級 の順 |
| リセット | 初期状態（§3.3.4）に戻る |

### 8.2 データ整合性テスト

`old/parts-data.js` と `old/rank-bonus-data.js` は素の `const X = ...` スクリプトである。
**これらのファイルを一切変更せず**、テスト側でテキストとして読み込み `new Function()` で
評価して比較する。

#### 8.2.1 パーツ（40件固定）

| 検証項目 | 内容 |
|---|---|
| 全数値の一致 | 40件の `cost` と5ステータスが旧データと完全一致する |
| パーツ名の一致 | 導出した40個の名前が旧データの `name` と完全一致する |
| 件数 | 4部位 × 10件 = 40件。**件数一致を検証する**（追加予定がないため） |
| 網羅性 | 各部位に 5系統 × (通常級/改級) が過不足なく存在する |

#### 8.2.2 ランクボーナス（拡張あり）

| 対象 | 検証項目 |
|---|---|
| ランク 1 〜 135 | 旧データの各 `rank` に対応する行が新データに存在し、`capacity` と5ステータスが完全一致する |
| ランク 136 以降 | **旧データとの比較を行わない** |
| 全ランク共通 | `rank` が 1 から始まる／欠番がない／重複がない／昇順である |
| 全ランク共通 | `capacity` と5ステータスがすべて存在し、すべて整数である |
| 全ランク共通 | `capacity >= 0` |
| `MAX_RANK` | テーブル末尾の `rank` と一致する |

**配列全体の件数一致は検証しない。** 旧データ側の各行に対応が存在するかを一方向に照合する。
これによりランク136以降を追加してもテストは壊れず、既存135件の値の退行は検出できる。

### 8.3 コンポーネントテスト

> **jsdom はレイアウト計算を持たない。** 要素の寸法・位置・実際の描画順は取得できず、
> `getBoundingClientRect()` は常にゼロを返し、CSS のカスケードやメディアクエリも評価されない。
> したがって本層で検証するのは **DOM構造・属性・イベント応答・状態遷移** に限る。
> 高さ・視覚順・レイアウトの成立可否は §8.4 で確認する。
>

| 対象 | 検証項目 |
|---|---|
| ランク入力欄 | §3.1.2 の各入力パターンで、状態・エラーメッセージの有無・文言が一致する |
| ランク入力欄（書き換え） | §3.1.3 の表どおり、入力中は値が書き換わらない。`blur` で `valid` のみ正準表現に整形される（`" 80 "`→`80`、`"１３５"`→`135`、`"01"`→`1`）。`invalid` / `empty` は無変換 |
| ランク入力欄（IME） | `compositionstart` 〜 `compositionend` の間は判定が更新されず、`compositionend` 後に再判定される |
| ランク入力欄（キー） | §3.1.5 の遷移表の全行を `keyDown` で検証する。`preventDefault` が呼ばれる |
| ランク入力欄（ARIA） | `aria-invalid` が状態に追従する。`aria-describedby` がエラー要素の `id` を指す。メッセージ領域が `aria-live="polite"` を持つ |
| セレクト | `<optgroup>` が5つ、`SERIES` 定義順に並ぶ。各グループ内が 通常級 → 改級 の順。全10件が存在する |
| セレクト | 選択肢の表示形式が `{パーツ名} (コスト{n})` である。先頭に未選択の選択肢がある |
| セレクト | `<label>` と `<select>` が関連付けられている |
| 性能表示 | パーツ選択でミニグリッドの値が更新される。未選択で `—` になる |
| 超過警告 | ランク `valid` かつ超過時のみ文言が出力され、超過量が正しい。ランク `empty` / `invalid` では出力されない |
| リセット | ランク・4部位・エラー状態が初期化される。フォーカスがボタンに残る |
| キーボード操作 | 全操作要素がフォーカス可能で、正の `tabindex` が存在しない。DOM上の出現順が期待順序と一致する（**視覚順との一致は §8.4**） |

### 8.4 手動確認項目

`tests/manual-checklist.md` に置き、リリース前に実行する。

**E2E（Playwright等）は導入せず、手動確認を正式な受け入れ条件とする。**
理由: レイアウトの成立・フォントの描画・フォーカスリングの視認性は実ブラウザでの
視覚判断が主であり、スクリーンショット照合で機械化すると環境差による偽陽性が多く、
維持コストが検証価値を上回ると判断した。
将来 E2E を導入する場合も、本チェックリストを置き換えるのではなく補完する位置づけとする。

**数px単位の位置・余白・文字幅・桁位置は検査しない**（§5.5.2）。
「ぱっと見で崩れておらず、操作・判読できる」ことを合格基準とする。

チェック項目:

- [ ] 幅 **960 / 1040 / 1440 px** で主要要素が重ならない
- [ ] 意図しない横スクロールが発生しない
- [ ] 文字や数値が表示領域から切れない（想定される最大値・最小値で確認。§4.3）
- [ ] ランク入力・4つのパーツ選択・リセットが操作できる
- [ ] 総合ステータスとキャパシティ超過警告が判読でき、他の操作要素に重ならない
- [ ] **Tab のフォーカス移動順が、画面上の視覚的な並び順と一致する**（jsdomでは検証不能なため必須）
- [ ] Tab でフォーカスを移動したとき、全操作要素でフォーカスリングが視認できる
- [ ] **日本語・数字・記号・ユーザー入力が判読でき、文字化けや豆腐（□）が発生していない**
- [ ] グレースケール表示でも正の値と負の値を区別できる（符号による識別）
- [ ] モックアップ「2c 松葉」と全体的な雰囲気が大きく異ならない

**検証しないもの**: 数px単位の位置、余白の厳密な一致、文字幅、桁位置、
特定のOSフォント名で描画されたか、合成ボールド、スクリーンショットのピクセル一致。

## 11. 未確定事項・申し送り

1. **`surveillance` と「巡航」の対応**【未確認】。§7.4 参照。旧名を踏襲し、確認でき次第
   改名を検討する。`labels.ts` に日本語表記を分離しているため影響範囲は閉じている
2. **旧SPEC 4.5 課題③（余裕度の可視化）は意図的に未解決**とした。将来、必要性が生じた場合は
   キャパシティゲージの再検討を行う
3. **データ構造の変更時**は全参照箇所の洗い出しが必要。特に `STAT_KEYS` / `SLOTS` / `SERIES` は
   表示順序と型の両方を規定しているため、順序変更が表示順に直結する
4. **ランク上限が拡張された場合**の変更箇所は `src/data/rank-bonus.ts` への行追加のみ。
   `MAX_RANK` は導出されるため、UI文言・バリデーション・↑↓キーの上限は自動的に追従する。
   §8.2.2 の検証設計により、行追加でテストは壊れない
5. **`--accent`（緑）と `--danger`（赤）は輝度がほぼ同一**である。将来トークンを調整する場合も、
   符号による識別（§5.3、§6 A7）を外してはならない
6. **E2E の導入**は現時点で見送っている（§8.4）。UIの複雑度が上がった場合は再検討する
7. **`box-sizing: border-box` はレイアウト破綻を防ぐ基本実装**である（§5.5.3）。
   CSSリセットを差し替える場合はこの指定が失われていないか確認すること
8. **UI は「ぱっと見で崩れておらず、操作・判読できる」ことを合格基準とする**（§5.5.2）。
   数px単位の位置・余白・文字幅・桁位置を仕様に書き戻さないこと。
   モックアップ「2c 松葉」は全体デザインの参考であり、厳密な再現対象ではない
9. **WCAG 1.4.10 リフローを対象外としている**（§6.1）。これは PC 幅960px以上のみを
   対象とする方針（§1）の帰結であり、アクセシビリティ上の後退である。
   対応範囲を広げる場合は §6.1 を削除し、狭いビューポート向けのレイアウトを
   §5.5 に追加すること
10. **フォントは OS 標準のものを使う**（§5.2）。書体差は許容し、厳密な書体・ウェイト・
    文字幅・桁揃えは保証しない。フォントをアプリから配信する方式に戻す場合は、
    ライセンス（再配布条件）と検証の設計を改めて行う必要がある
